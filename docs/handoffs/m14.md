# Nota de entrega — M14 (sincronización offline-first)

## Entrega: lead · M14

**Hecho:**

- Cliente autenticado y validado con Zod para listar, guardar y borrar
  contactos y alertas.
- Orquestación offline-first: vinculación de cuenta, subida de pendientes,
  descarga incremental, tombstones, cursores y protección frente a cambios
  locales concurrentes.
- Sincronización automática al restaurar sesión y al volver a primer plano;
  estado y reintento accesible en Ajustes. El cierre de sesión espera el trabajo
  activo.
- Cursor compuesto `(updated_at, id)` para paginar sin omitir registros que
  compartan timestamp.

**Archivos:** `src/api/sync.ts`, `src/api/contracts/index.ts`,
`src/sync/sincronizar.ts`, `src/sync/mapeo.ts`,
`src/controllers/useSincronizacionController.ts`,
`src/controllers/sesionContext.tsx`, `src/repositories/contactos.ts`,
`src/repositories/alertas.ts`, `app/ajustes.tsx`,
`docs/api-contrato.md`, `docs/specs/m14-sincronizacion.md` y pruebas asociadas.

**Cómo verificar:**

- `npm run lint` — pasa.
- `npm run typecheck` — pasa.
- `npm test -- --runInBand` — 53 suites y 538 pruebas pasan.
- Prettier ejecutado en archivos modificados; `git diff --check` — sin errores.

**Decisiones:**

- SQLite sigue siendo la fuente local; cursor y usuario vinculado se guardan en
  `ajustes`, nunca los tokens.
- El primer intento de sincronización de una sesión vincula el dispositivo a
  esa cuenta; cuentas distintas quedan bloqueadas para no mezclar datos.
- El GET incremental usa cursor compuesto en páginas posteriores para resolver
  empates de `updated_at`.
- `principal` forma parte del contrato de contactos, según la decisión previa
  de M5.

**Pendiente / bloqueos:**

- Zona `api` en `boton-de-seguridad-api`: implementar `principal` y el parámetro
  `after_id` según `docs/api-contrato.md`. Este repositorio móvil no modifica la
  API ni valida una integración real contra ella.
- No se creó commit ni se hizo push de M14.

**Dudas de la especificación:** ninguna pendiente en el cliente móvil. El
contrato compartido actualizado debe aplicarse también en el repositorio de la
API antes de desplegar.

**Revisión de seguridad:** no se solicitó una revisión de seguridad dedicada.
El cliente reutiliza el Bearer token existente y no almacena credenciales en
SQLite; la sincronización no envía SMS. La protección de aislamiento depende
también de que la API limite cada consulta y mutación a la cuenta autenticada.
